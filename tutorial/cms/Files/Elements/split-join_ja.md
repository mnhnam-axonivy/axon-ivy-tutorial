# Split と Join

`Split` · `Join` · Axon Ivy 14.0

## どんな要素で、いつ使うか

2つは一緒に使います:「この要素は必ず Join 要素と一緒に使ってください。」

- **Split**:「並行するプロセスパスをモデル化できます。」1つのプロセスパスを「同時に実行される複数のパスに分ける」ことができます。「入力のプロセスデータはすべての並行実行にコピーされますが、各パスで個別に変更できます。」
- **Join**:「この要素は、並行して実行されるプロセスパスを同期し、1つにまとめます。入ってくる各パスの出力が要素にコピーされ、その出力の定義に使えます。」「入ってくる並行のプロセスパスがすべて終わり、この要素に到達するまで待ちます。」

キャンバスでは、どちらも + の付いたひし形です。リファレンスにはヒントがあります:「Split と Join を使って、データベースや Web サービスへのリクエストを並行して実行します。」

| したいこと | 使う要素 |
| --- | --- |
| 互いに独立したことを複数行い、すべて終わったら先に進む | Split、次に Join |
| いくつかのパスから1つを選ぶ | Alternative |
| 分かれたパスを再び合流させる | Alternative（Join ではない） |

## 詳細

### Split

**一般** と **出力** の2つのタブがあります。

| セクション | 役割 |
| --- | --- |
| マッピング | 出ていくコネクターごとにルートが1つ: `out1`、`out2`、…。それぞれがそのパスのプロセスデータで、属性ごとに1行があります。「出ていく接続ごとに、X 番目の出力のデータを運ぶ `outX` オブジェクトがあります。」Designer では、コネクターにマウスを置くと、どの変数を運ぶかが表示されます。 |
| コード | マッピングの後に実行される IvyScript。`in` と `out1`、`out2`、… が使えます。 |

新しい Split がマッピングするのは `out1` ← `in` だけです。プロセスファイルでは、出ていく各コネクターが自分の変数を指定します（`"outVar" : "out2"`）。

### Join

**一般** と **出力** の2つのタブがあります。

| セクション | 役割 |
| --- | --- |
| マッピング | 先に進むデータ `out`。属性ごとに1行があります。「入ってくる接続ごとに、X 番目の入力のデータを運ぶ `inX` オブジェクトがあります。」`in` はありません。新しい Join は `out` ← `in1` をマッピングします。 |
| コード | マッピングの後に実行される IvyScript。`out` と `in1`、`in2`、… が使えます。 |

プロセスファイルでは、入ってくる各コネクターが自分の変数を指定します（`"var" : "in2"`）。

### 実行時

1. Split は、出ていく各コネクターに自分のトークンを与えます。データは `outX` の行のとおりです。行のない `outX` は、新しい空のデータから始まります。
2. パスは1要素ずつ交互に進みます。エンジン 14.0.1 では2つ目のパスが先でした。2つのパスは `b1 a1 b2 a2`、3つのパスは `2, 3, 1` の順です。Axon Ivy コミュニティによると、Split のパスは同じスレッドで実行されるので、並行は見かけだけです。本当に並行して進むのは、Program Interface、Database、Web Service Call のように自分のスレッドで動く要素です（[answers 329](https://answers.axonivy.com/questions/329/multi-threading-in-ivy-processes.html)、2010年）。
3. Join に到達したトークンはそこで待ちます。入ってくるすべてのコネクターでトークンがそろうと、Join は「出力」を実行し、1つのトークンが `out` で先に進みます。
4. 既定の `out` ← `in1` では、1つ目のパスのデータが先に進み、ほかのパスが変えたものは、行で取らない限り失われます: `out.references` ← `in2.references`。
5. 入ってくるパスの数より少ないパスしか到達しない Join は、トークンを持ったままです。その後は何も実行されず、リクエストはエラーなしで終わります。
6. Join で `in` を使うと失敗します。Designer は `Output code: Variable 'in' cannot be resolved` と報告します。

1、2、4〜6 はドキュメントに記載がありません。2026-11-16 に Designer とそのエンジン 14.0.1 で確認したものです。

## よくある質問

**パスは本当に同時に実行される？**
1つのスレッドの中で、1要素ずつ交互に進みます。計算だけのステップは並行にしても速くなりません。Split が効くのは、答えを待つほかのシステムへの呼び出しです。

**パスはどの順で実行される？**
順序を前提にしないでください。エンジン 14.0.1 では2つ目のパスが先でした。互いの結果を必要とするパスは並行ではありません。順に並べます。

**2つ目のパスでデータが空なのはなぜ？**
新しい Split がマッピングするのは `out1` ← `in` だけです。すべての `outX` を `in` からマッピングします。

**すべてのパスの結果を受け取るには？**
Join の「出力」で受け取ります。`out` ← `in1` で1つ目のパスのデータを取り、ほかのパスの結果はそれぞれの `inX` から1行ずつ取ります。

**あるパスが Join に届かないとどうなる？**
Join はそのパスを待ち、プロセスは Join の後に進みません。Split が開始するすべてのパスが Join につながるようにします。

## よくある間違い

### 2つ目のパスにデータがない

- *症状:* 後のパスのステップが空の属性を見つける。例えば "References of : good"。実行は失敗しない。
- *原因:* その `outX` に行がない。新しい Split がマッピングするのは `out1` ← `in` だけ。
- *直し方:* すべてのパスをマッピングする: `out2` ← `in`、`out3` ← `in`、… [ウォークスルー 3.7](#/walkthrough/3.7)

### Join が1つのパスだけを残す

- *症状:* Join の後、あるパスが設定した値がない。
- *原因:* Join が `out` ← `in1` をマッピングしていて、ほかのパスが変えたものを取っていない。
- *直し方:* 結果ごとに行を追加する: `out.references` ← `in2.references`。[ウォークスルー 3.7](#/walkthrough/3.7)

### Join で `in`

- *症状:* Designer が `Output code: Variable 'in' cannot be resolved` と報告する。
- *原因:* Join には入ってくるパスごとの `inX` があり、`in` はない。
- *直し方:* 値がどのパスから来るのかを書く: `in1.name`。[ウォークスルー 3.7](#/walkthrough/3.7)

### 分かれたパスの後の Join

- *症状:* Join の後に何も実行されず、ランタイムログにエラーもない。
- *原因:* パスが Alternative から来ているので、選ばれるのは1つだけで、Join はほかのパスを待っている。
- *直し方:* 分かれたパスは Alternative で合流させる。Join が閉じるのは Split が開いたパスだけ。[ウォークスルー 3.6](#/walkthrough/3.6)

### 互いに依存するパス

- *症状:* あるパスが、別のパスが設定する値を読み、空か古い値を見つける。
- *原因:* 各パスは自分のデータのコピーを持つ。あるパスが変えたものは、Join までほかのパスには見えない。
- *直し方:* 依存するステップは順に並べ、結果は Join でまとめる。
